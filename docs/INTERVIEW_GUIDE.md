## 1. 30秒説明

> 東京都が公開している地価公示と基準地価のオープンデータ（4ファイル・約7,600地点）を使い、
> **翌年の平米単価（円/㎡）を予測する機械学習パイプライン**を作りました。
> 目的変数は地点の総額ではなく平米単価です。総額だと「広いほど高い」という自明な関係を
> 当てるだけになるからです。特徴量は地点属性と前年の実測単価で、前年価格・対前年変動率という
> 強いリーク列は構造的に排除しています。時系列分割（令和7年で学習→令和8年を予測）で評価し、
> LightGBM で MAE 約1,300円/㎡、前年単価をそのまま使うベースラインが MAE 約750円/㎡でした。
> **機械学習が効く範囲と効かない範囲を切り分けた**のが結論です。

## 2. 1分説明

> 中古住宅価格予測をやりたかったのですが、実データの制約で**東京都の公式地価**に変更しました。
> 理由は2つで、1つは地点属性（容積率・建蔽率・駅距離・前面道路幅員・用途区分）が
> 公式に揃っていること、もう1つは取引価格データ（不動産取引価格情報）がAPIキーを必要とし
> **第三者が再現できない**ことです。再現性を優先しました。
>
> パイプラインは `python -m src.pipeline` の1コマンドで完結します。生CSVは CP932・
> タイトル行つき・数値がカンマと末尾スペース入りの文字列で、年度によって和暦の表記も
> 括弧の全角半角も違うので、そこを丁寧にクリーニングしています。
>
> 設計上の一番の判断は**リーク対策**です。`前年価格` と `対前年変動率` は同じ年の価格から
> 作られた列なので、目的変数と0.95の相関があります。これを入れると test MAE が
> 約1,300円/㎡から約800円/㎡に「改善」して見えますが、それは予測ではなく答えの言い換えです。
> 特徴量の許可リストを1箇所（`features.feature_columns`）に集約し、
> リーク列は明示フラグを立てた統制実験でしか入らないようにし、pytest で検証しています。
>
> もう1つは**地点IDによるパネル化**です。市区町村コード＋用途＋連番で年度をまたいで
> 地点を対応づけ、前年ファイルから**実測の前年単価**を結合します。カバレッジは98.4%です。
>
> 評価は時系列分割で、train=令和7年、val/test=令和8年（地点単位で排他）です。
> 結果として、勾配ブースティングは「前年単価 × 1.05」という単純なベースライン
> （MAE 477 円/㎡）を超えられませんでした（最良の学習モデルで 1,282 円/㎡）。
> 原因も特定していて、令和8年は 97.5% の地点で価格が上昇した年なので、
> 課題の本質は「水準の予測」ではなく「変化率の予測」でした。
> 変化率を目的変数にした追試も行いましたが、2年分のデータでは学習できず
> 改善しませんでした。**この負の結果を隠さず報告する**ことを選んでいます。

## 3. 開発背景

- **出発点**: 中古住宅価格予測（Kaggle の House Prices 的な課題）をやりたかった。
- **障壁**: 日本の住宅取引データは以下が問題になる。
  - 不動産取引価格情報（国交省）は API キーが必要で、面接官が clone しても動かない。
  - 民間ポータルの価格データはスクレイピング規約・再配布ライセンスが不明確。
  - 住宅価格は「建物」の情報（築年数・間取り・リフォーム履歴）が本質だが、
    それを公式に一括取得できるオープンデータが存在しない。
- **転換**: 東京都財務局の地価公示・基準地価は、
  - オープンデータ（CC BY 4.0 相当）で再配布可、
  - **地点属性が官公庁の基準で統一**されている（容積率・建蔽率・駅距離・道路幅員など）、
  - 全地点に**平米単価が公式に定義**されている（当年価格 ÷ 地積）、
  - 年度をまたいで同一地点を追跡できる（地点番号が継続する）。
- **誠実さの担保**: README 冒頭で「地価であって住宅価格ではない」と明記し、
  Limitations に制約を列挙。誇張した数値は一切載せていない。

## 4. Architecture

```
data/raw/*.csv  (4ファイル, 無改変)
      │
      ▼
src/data_loader.py     CP932/タイトル行/括弧ゆれ を吸収。列名をASCII化
      │                drop_trailing_blank_rows で最終空行のみ除去
      ▼
src/cleaning.py        to_number (カンマ・全角) / parse_wareki_year / parse_floor_count
      │                add_unit_price: unit_price = 当年価格 ÷ 地積
      ▼
src/features.py        build_features: 帯化・容積建蔽比・カテゴリ補完
      │                attach_lag_unit_price: 前年ファイルとの地点キー結合
      │                ★ feature_columns(): 特徴量ホワイトリスト = リーク防壁
      ▼
src/pipeline.py        build_split: train(令和7年) / val,test(令和8年, 地点排他)
      │                fit_and_score: 特徴量を train から凍結 → 全 split で同一列
      ▼
src/models.py          build_estimator: ModelPipeline(preprocessor + estimator)
      │                TargetLogRegressor: log1p → expm1 で逆変換
      │                LGBMCategoricalRegressor: カテゴリ列を LightGBM に宣言
      ▼
src/evaluate.py        regression_metrics (MAE/RMSE/R2/MAPE) / KFold CV
      │                temporal_split / random_split (統制実験用)
      ▼
src/error_analysis.py  区・用途・価格帯・地積帯・駅距離帯・容積率帯で誤差を集計
      │                仮説検証（容積率プレミアム / 小規模地 / 駅距離）
      ▼
src/plots.py           8枚の図を matplotlib で生成（英語ラベル）
      ▼
reports/               metrics.json + 3本の Markdown（すべて自動生成）
```

**設計原則**

1. **単一の真実**: 特徴量の定義は `features.feature_columns()` のみ。
2. **再現性**: 乱数シード・分割・モデル設定は `configs/config.yaml`。
3. **観測可能**: ログに全判断（ラグのカバレッジ、除外した特徴量、CV結果）を出す。
4. **過剰設計しない**: 抽象化レイヤを増やさず、関数とデータクラスで構成。

## 5. 技術選定理由

| 選定 | 理由 | 代替案を採らなかった理由 |
|---|---|---|
| **Python 3.13 + pandas** | 表形式・カテゴリ混在・日本語列名の扱いに最も実績がある | Polars は速いが、カテゴリ処理とエコシステムの成熟度で pandas を選択 |
| **scikit-learn** | Pipeline/ColumnTransformer で**前処理を fold 内に閉じ込められる**。CV も統一API | 自前実装はリークの温床になる |
| **LightGBM** | カテゴリをネイティブに扱える。欠損をそのまま扱える。表形式で最高水準 | XGBoost はカテゴリ指定が煩雑。CatBoost は実装は楽だが依存が重い |
| **RandomForest / GradientBoosting** | 比較対象として。過学習の度合いを実測で示すため | — |
| **Ridge** | 線形の基準点。木モデルとの差＝非線形性の寄与を切り分ける | — |
| **対数変換** | 目的変数が5桁の幅（0.2〜148,000円/㎡） | Box-Cox は負値・ゼロを扱いにくく、log1p で十分 |
| **OrdinalEncoder（木） / OneHotEncoder（線形）** | 木は順序を分割に使える。線形は整数コードに順序を仮定できない | ターゲットエンコーディングは**リーク源**になるため不使用 |
| **matplotlib** | 依存が軽く、図の再現性が高い | seaborn は表現力は高いが、この規模では不要 |
| **pytest** | 標準。テストが仕様書として機能する | — |
| **YAML 設定** | 実験条件を差分でレビューできる | argparse のみでは履歴が残らない |

## 6. 一番苦労した点

**「良く見えるスコア」と「本当に予測できているか」を切り分けたこと。**

最初に動くモデルを作ったとき、決定木系の R² が 0.99 に近い値で出ました。
しかし内訳を見ると **train MAE が 88 円/㎡、test MAE が 1,287 円/㎡**で、
train の誤差が test の 1/15 でした。これは「学習地点を丸暗記している」状態です。

地価データは空間的自己相関が極端に強く、同じ町名・同じ用途の地点はほぼ同じ価格になります。
ランダム分割だと同じ町の地点が train と test の両方に入り、
**モデルは「近所の価格を思い出す」だけで高スコアを出せてしまいます**。

対処として、
1. 分割を**時系列**（令和7年 → 令和8年）にし、
2. さらに val / test を**地点単位で排他**にし、
3. `lag_unit_price`（前年単価）という**最も強い正当なベースライン**を用意して、
   「MLが何も足せていない」可能性を常に可視化しました。

結果として「勾配ブースティングは前年単価ベースラインに勝てない」という
**あまり格好良くないが正直な結論**にたどり着きました。
これを隠さず報告することが、実務では一番重要だと考えています。

## 7. 発生したバグ（実際のもの）

面接で「実際に詰まった点」を聞かれたら、この中から2〜3個を具体的に話してください。

### 7.1 列名の括弧が全角と半角で混在していた（最重要）

- **症状**: クリーニング後の DataFrame に `station_distance` が存在せず
  `KeyError: 'station_distance'` でパイプラインが停止。
- **原因**: 地価公示は `交通施設までの道路距離（m)`（**開き全角 `（` + 閉じ半角 `)`**）、
  基準地価は `（m）`（両方全角）。列名正規化で空白だけを除去していたため、
  公示側のキーが `COLUMN_MAP` にヒットしなかった。
- **対処**: `_normalise_name` で括弧を全角に統一してからマップを引くように変更。
  さらに `COLUMN_MAP` の全キーが正規化済みであることを確認する
  ワンライナー検証を開発中に実行した。
- **結果**: 4ファイルすべてが同一の内部列名に揃い、
  `tests/test_cleaning.py::test_bracket_variants_are_normalised` で回帰テスト化。

### 7.2 「97.8% 一致するはずの前年価格が 42% しか一致しない」

- **症状**: 行番号で `kouji_r8["前年価格"] == kouji_r7["当年価格"]` を比較すると
  一致率 42%。データが壊れていると誤解しかけた。
- **原因**: **2つの年度ファイルの並び順が同一ではない**。
  さらに用途コードが同じで連番が違う地点があり、行の位置がずれていた。
- **対処**: 地点キー（市区町村コード＋用途＋連番）で整列してから比較。
  キー一致率は **98.4%**（2,518 / 2,560）で、キーが一致した地点は
  **前年価格が前年の当年価格と1円の狂いもなく一致**します（最大絶対差 0 円）。
  残る 42 地点は新規に選定された標準地です。
- **結果**: この「キーで結合する」という発見が**パネル化の設計そのもの**になった。
  教訓は「年度をまたぐデータは行番号で対応づけてはいけない」。

### 7.3 前年単価ベースラインが KeyError で動かない

- **症状**: `LagBaseline` を実行すると
  `KeyError: "LagBaseline requires the 'lag_unit_price' feature"`。
- **原因**: 特徴量解決ロジックが「学習データに信号がない列は除外する」ため、
  令和7年（前年ファイルが存在しない年）では `lag_unit_price` が正しく除外され、
  結果としてベースラインが参照する列そのものが消えていた。
- **対処**: **評価用フレームにも実測ラグを結合する**よう変更。
  令和8年ファイルの `前年価格` 列は令和7年の価格を再掲しており、
  逆に令和7年の価格は（翌年を予測する時点で）既知である、という双方向の関係を使い、
  train と test の双方に「実際に入手可能な前年単価」を持たせた。
- **結果**: ラグのカバレッジが train / predict ともに 98.4% になり、
  ベースラインと ML モデルを**同じ情報量の土俵**で比較できるようになった。
  これは「ベースラインが弱すぎて ML が勝ったように見える」という
  ありがちな失敗を防いでいる。

### 7.4 決定木の特徴量重要度が1列しか出ない

- **症状**: 重要度テーブルが `num_lag_unit_price: 1.0` の1行だけ、
  あるいは Ridge では空になった。
- **原因**: 3つの独立したバグが重なっていた。
  1. `set_output(transform="pandas")` をネストした Pipeline に適用すると、
     scikit-learn のバージョン差で列名が失われる。
  2. 前処理が出力する列数（ワンホット後 245 列）と、
     特徴量名リストの長さ（ordinal 前提の 24）が一致していなかった。
  3. ワンホット列名から元の特徴量を復元する処理が**部分文字列一致**だったため、
     `locality` が `municipality` に誤マッチしていた。
- **対処**:
  1. `set_output` を捨て、**明示的なラッパー**（`ModelPipeline`）で
     DataFrame 変換を1箇所に集約。
  2. 列名を**エンコーダの出力**から生成（`DataFrameOutput._column_names`）。
  3. 部分文字列一致を**完全な前置一致**（`token == col or token.startswith(col + "_")`）に変更。
  4. ワンホットで膨らんだ重要度を元の特徴量単位に**合算**し、
     全モデルを同じ特徴量名で比較できるようにした。
- **結果**: 4モデルすべてで解釈可能な重要度が出るようになり、
  `tests/test_models.py::TestFeatureImportance` で回帰テスト化。

### 7.4b `road_width = 0` の地点が帯化で消えていた

- **症状**: 道路幅員帯（`road_width_band`）が 29 地点で `NaN`。
  しかし元の `road_width` は欠損していない。
- **原因**: `pd.cut(bins=[0, 4, 6, ...], right=True)` は **0 を含まない**ため、
  道路幅員 0 m の地点がどのビンにも入りませんでした。
  0 m は「接道していない」という公式の記録方法で、意味のある値です。
  同じ理由で地積帯にも潜在的な穴がありました。
- **対処**: 最初のビン端を `-inf` に変更。
- **結果**: 「帯は元の列が欠損している場所でのみ欠損する」ことを
  `tests/test_features.py` でパラメータ化して保証。
  **エラーが出ないままデータが減る**タイプのバグで、
  「変換前後で件数と欠損数を突き合わせる」習慣の重要性を示しています。

### 7.4c 和暦パーサが全行 `NaN` を返していた（無音の失敗）

- **症状**: クリーニング後の `year` が全て欠損。ただし例外は出ない。
- **原因**: `numpy.where` の結果を pandas Series に代入する際、
  `pd.to_numeric` が返す Series の**インデックスと位置がずれ**、
  結果が `NaN` で上書きされていました。
  加えて `'7 '` のような素の数値を「西暦7年」と解釈していました。
- **対処**: numpy 配列で計算し最後に Series に戻す実装に変更。
  「1868 以上は西暦、それ未満は令和の年号」という規則を明示。
- **結果**: `'7 '` → 2025、`'令和8年'` → 2026、`'平成30年'` → 2018。
  インデックス保持を検証するテストを追加。

### 7.4d 勾配ブースティングが負の地価を予測した

- **症状**: LightGBM の予測に負値が混入し、`assert (pred >= 0).all()` が失敗。
- **原因**: raw の目的変数に対する二乗誤差回帰には非負制約がなく、
  山林・島しょ部の安価な地点で負値を返すことがありました。
- **対処**: `NonNegativeRegressor` ラッパーで 0 クリップ。
  モデリングのトリックではなく**ドメイン制約**であり、
  全モデルに同じ扱いを適用して比較の公平性を保っています。
- **結果**: 全モデルで `0 <= 予測値` が保証され、テストで検証。

### 7.5 LightGBM がロードできない（`libomp.dylib` 不在）

- **症状**: `import lightgbm` が
  `OSError: dlopen(...lib_lightgbm.dylib...): Library not loaded: @rpath/libomp.dylib`。
- **原因**: macOS の LightGBM wheel は OpenMP ランタイムを動的リンクするが、
  Homebrew の `libomp` が入っていなかった。加えて `libomp` は PyPI に存在せず
  `uv pip install libomp` では解決できない。
- **対処**: システムに既にあった R.framework 同梱の `libomp.dylib`
  （arm64/x86_64 ユニバーサル）を実行時に `DYLD_LIBRARY_PATH` で参照。
- **結果**: LightGBM 4.7.0 が動作。README のセットアップに
  「`brew install libomp` が必要」と明記し、
  macOS 以外では不要であることも併記した。

### 7.6 LightGBM のログがパイプラインのログを埋め尽くす

- **症状**: `verbose=-1` を指定しているのに
  `[LightGBM] [Info] Auto-choosing col-wise multi-threading...` が大量に出る。
- **原因**: LightGBM の C++ 層が Python の `logging` 経由で INFO を出力するため、
  `verbose=-1`（Booster の設定）では止まらない。
- **対処**: `lightgbm.register_logger()` に `propagate=False` の
  ヌルハンドラ logger を渡す `quiet_lightgbm()` を追加。
- **結果**: パイプラインのログが実質的な情報（MAE、カバレッジ、除外した特徴量）だけになり、
  実行ログをそのまま README に貼れるようになった。

## 8. どう解決したか（デバッグの進め方）

一貫して使った手順です。面接で「デバッグの進め方」を聞かれたらこの型で答えてください。

1. **再現する最小ケースを作る**: パイプライン全体を回さず、
   `data_loader` → `cleaning` → `features` を1セルずつ実行して切り分ける。
2. **仮説を言語化してから計測する**: 「行番号で比較しているからずれるはず」→
   実際に両方の一致率を並べて出力する。
3. **中間物の形を必ず確認する**: `X.shape`、`len(feature_names)`、
   実際に前処理が出力した列数。**shape の不一致は必ずバグ**。
4. **直したらテストにする**: 7.1〜7.4 はすべて pytest の回帰テストとして残っている。
5. **ログに残す**: 「どの特徴量を、なぜ除外したか」を INFO で出す。
   サイレントに落とすと後で必ず事故になる。

### 7.7 「機械学習がベースラインに勝てない」という結果をどう扱ったか

これはバグではありませんが、**一番判断に迷った点**なので記録します。

- **症状**: `前年単価 × 1.05` というベースライン（MAE 477 円/㎡）が、
  RandomForest（1,282）・LightGBM（1,348）を大きく上回った。
- **原因（実測に基づく仮説）**: 令和8年は **97.5% の地点で価格が上昇**した年で、
  前年比倍率の中央値は 1.0714。つまり課題の本質は
  「水準の予測」ではなく「**変化率の予測**」でした。
  ところが全モデルが「翌年の水準を地点属性から当てる」定式化になっており、
  構造的に変化率を表現できていません。
- **対処**: 変化率（`unit_price / lag_unit_price` の対数）を目的変数にした
  モデルを実際に作り、`lag × exp(予測対数比)` で復元して評価しました。
- **結果**: test MAE **1,339 円/㎡**（R² 0.938）で、**改善しませんでした**。
  前年比の分散が小さく（std 0.1018）、2年分のデータでは
  変化率のパターンを学習する信号が足りないという結論です。
- **判断**: この負の結果を**隠さずレポートに記載**しました。
  「ML を適用したが、この設計では baseline に勝てなかった。
  その理由はデータの年数と目的変数の定式化にある」まで言えることが、
  実務では最も価値のある報告だと考えるからです。

## 9. 改善するとしたら

優先度順に、実現可能性も添えて。

1. **空間特徴量の追加（最重要）**
   現在 `municipality`（区市町村）までしか地理情報がない。
   緯度経度は本データに含まれないが、町丁目レベル（`locality`）は持っている。
   町丁目をターゲットエンコーディング（**CV内で**計算する版）や
   近傍地点の平均単価（k-NN、ただし必ず前年以前のデータのみ）で特徴量化すれば、
   駅距離の粗さを補える可能性が高い。
2. **ハイパーパラメータ探索**
   今回は config に固定値を置いた。`Optuna` 等で探索し、
   **時系列分割の val で選択**（test は最後まで触らない）すれば改善余地がある。
3. **モデルの目的関数を相対誤差にする**
   MAE は円/㎡の絶対誤差なので高額地点に引っ張られる。
   `objective="regression_l1"` や log 空間での学習を体系的に比較する。
4. **公示地価と基準地価の統合**
   現在は別系列として扱っている。両者を1つのパネルに統合できれば
   学習データが約1.5倍になるが、**価格水準が系統的に異なる**ため
   系列フラグを立てた上での慎重な検証が必要。
5. **時系列モデル**
   地点ごとに3年以上の系列が取れれば、前年比の変化率自体を予測する
   （階差を取る）アプローチが考えられる。現状は2年分しかないため不可能。
6. **不確実性の提示**
   実務では点推定より区間が欲しい。分位点回帰（LightGBM の
   `objective="quantile"`）で予測区間を出し、被覆率で評価する。

### Machine Learning 基礎

**Q1. 教師あり学習とは何か。このプロジェクトはどの型か。**
入力 X から目的変数 y を予測する関数を、正解ペア (X, y) から学習すること。
本プロジェクトは **回帰**（y が連続値 = 平米単価）。
分類（用途区分の予測）ではない。目的変数を `unit_price = 当年価格 ÷ 地積` と定義し、
`X = 地点属性 + 前年実測単価`、`y = 翌年の平米単価` という教師あり回帰として定式化した。

**Q2. なぜ「住宅価格」ではなく「地価」なのか。**
地点属性（容積率・建蔽率・駅距離・道路幅員・用途区分）が官公庁の基準で統一されており、
年度をまたいで同一地点を追跡でき、ライセンスも明確（CC BY 4.0 相当）だから。
住宅の建物情報（築年数・間取り）を公式に一括取得できるオープンデータは存在しない。
また取引価格データは API キーが必要で**第三者が再現できない**ため再現性を優先した。
README 冒頭と Limitations に明記している。

**Q3. 目的変数に総額ではなく平米単価を選んだ理由は。**
`当年価格（円）` は地点の総額なので、総額を予測すると
「面積が大きいほど高額」という自明な関係を当てるだけのモデルになる。
実測では 地積↔総額 の相関が +0.053、地積↔平米単価 が −0.038 で、
平米単価にすると「広い土地は㎡あたり割安」という不動産として自然な方向になる。
`tests/test_features.py::TestTarget` で検証している。

### Regression

**Q4. 線形回帰と Ridge の違いは。なぜ Ridge を使ったか。**
線形回帰は二乗誤差を最小化する。Ridge は係数に L2 正則化を加え、
多重共線性による係数の発散を抑える。
本プロジェクトの特徴量は容積率と建蔽率（相関が高い）、地積と地積帯（ほぼ同一情報）など
**強く相関する列が多い**ため、正則化のない線形回帰より Ridge が安定する。
実測でも Ridge は train MAE 1,430 円/㎡・test MAE 1,609 円/㎡で
過学習ギャップが 1.13 倍と小さく、線形の基準点として機能した。

**Q5. 回帰で気をつける前処理は。**
(1) スケーリング（Ridge は必須）、(2) 欠損の補完（中央値）、
(3) カテゴリのエンコード、(4) 外れ値・分布の歪み。
**すべてを Pipeline の中に入れ、学習 fold だけで fit する**のが最重要。
本プロジェクトは `ColumnTransformer` で数値（中央値補完＋標準化）と
カテゴリ（エンコード）を分け、`ModelPipeline` の中で fit するので、
CV や val/test に学習統計が漏れない。

**Q6. なぜ複数のモデルを比較するのか。**
単一モデルでは「その精度が良いのか悪いのか」の基準がない。
本プロジェクトは 7 つ（median, mean, lag, ridge, random_forest,
gradient_boosting, lightgbm）を同一分割で比較し、
**定数予測（MAE 4,911）→ 線形（1,609）→ 木（1,282）→ 前年単価ベースライン（749）**
という序列を実測で示した。ベースラインを含めることで
「ML が何も足していない」可能性を可視化している。

### Train / Validation / Test

**Q7. 3分割する理由は。2分割ではだめか。**
2分割だとモデル選択と性能報告に同じデータを使うことになり、
**テストセットに適合するように選択してしまう**（選択バイアス）。
本プロジェクトは val（令和8年の1,280地点）で最良モデルを選び、
test（**排他の**もう1,280地点）で最終報告する。
実際 val MAE 1,242 と test MAE 1,282 は近く、分割が安定していることを確認している。

**Q8. val と test をどう分けたか。**
令和8年の2,560地点をシード固定（42）の `np.random.default_rng` で
無作為に半分に分けた。**地点単位で排他**であり、
`set(val["_site_key"]) & set(test["_site_key"])` が空であることを
`build_split` がアサートし、テストでも検証している。
ファイル先頭/後半で分けなかったのは、ファイルの並び順が
千代田区→島しょ部という地理順で、比較が地理に交絡するため。

**Q9. train と test の分布が違う場合どうするか。**
本プロジェクトがまさにその状況。train は令和7年、test は令和8年で、
**1年分の価格上昇**が含まれる（中央値が 3,094 → 3,336 円/㎡）。
対処として、(1) 前年単価を特徴量に入れて水準差を吸収させ、
(2) 対数変換で相対誤差として扱い、
(3) 誤差を価格帯別に集計して**どの帯で外すか**を明示した。
分布シフトを無視せず、報告に含めるのが正しい対応。

---

### Cross Validation

**Q10. Cross Validation とは。何のためにやるか。**
データを K 個に分け、1つを検証・残りを学習に使うことを K 回繰り返し、
平均と分散で性能を評価する方法。目的は
(1) 分割運によるブレの把握、(2) データ量が少ないときの有効活用、
(3) ハイパーパラメータ選択の安定化。
本プロジェクトは訓練年（令和7年・2,560地点）で 5-fold CV を行い、
LightGBM の CV MAE は平均 633・標準偏差 212 円/㎡だった
（**平均に対して標準偏差が 33% あり、分割次第で結果が動く**ことが分かる）。

**Q11. なぜ TimeSeriesSplit を使わなかったのか。**
TimeSeriesSplit は「1つの系列を時系列で分割する」ためのもの。
本プロジェクトの訓練データは**令和7年という単一の時点**なので、
行を時系列順に並べても意味のある順序が存在しない（1年＝1タイムスタンプ）。
無理に使うと「同じ年の前半で学習して後半を評価」という
**ランダム分割と同じ補間タスク**になり、時系列CVの利点が得られない。
そのため「訓練年内は KFold、年をまたぐ評価は時系列分割」という
**二層構造**にした。この判断は `src/evaluate.py` の docstring に記録している。

**Q12. CV のスコアと test のスコアが大きく違ったらどう考えるか。**
主な原因は (1) 分布シフト、(2) リーク、(3) データ量不足、(4) 分割の仕方の違い。
本プロジェクトでは CV MAE 633 円/㎡ に対し test MAE 1,282 円/㎡ で約2倍の差がある。
これは **CV が「同じ年の別地点」を当てている（補間）**のに対し、
test は**翌年・別地点（外挿）**だから。この差自体が
「ランダム分割のスコアは楽観的」という本プロジェクトの主張の根拠になっている。

### Overfitting

**Q13. 過学習とは。どう検出するか。**
学習データに適合しすぎて、未知データで性能が出ない状態。
検出は **train と val/test の乖離**を見る。
本プロジェクトの `random_forest` は train MAE 114 円/㎡・test MAE 1,282 円/㎡で
**乖離 11.2 倍**、明確な過学習。`ridge` は 1.13 倍でほぼ過学習なし。
`reports/model_comparison.md` に全モデルの乖離率を表で出している。

**Q14. 過学習の対策を挙げよ。実際にやったことは。**
対策: (1) データ増、(2) モデルの複雑度削減、(3) 正則化、(4) 早期終了、
(5) 特徴量削減、(6) アンサンブル。
本プロジェクトで実際にやったのは、
**RandomForest / GradientBoosting / LightGBM の木の深さ・葉の数を制限**し
（`min_samples_leaf=2`、`num_leaves=31`、`max_depth=4`）、
**正則化（`reg_lambda=1.0`）**を入れ、
**サブサンプリング（`subsample=0.9`）**を有効にした。
それでも train/test 乖離は残っており、**根本原因はデータ量（2,560地点）と
空間的自己相関**であると結論している。

**Q15. 訓練データを増やせば過学習は解決するか。**
単純には解決しない。本課題では「同じ町名の地点が学習にも評価にもある」ことが
問題の本質で、データを増やすと**むしろ同一町名の重複が増えて楽観バイアスが強まる**。
必要なのは「地点を分けた分割」と「空間的に離れた地点での評価」。
これは `Limitations` と `Future Work` に書いている。

### Data Leakage

**Q16. データリークとは。このプロジェクトでの具体例は。**
予測時点で手に入らない情報が、学習時に特徴量として入ってしまうこと。
本プロジェクトの具体例は **`前年価格（円）` と `対前年変動率（％）`**。
これらは同じ年の価格から計算された列で、目的変数と **0.95** の相関がある。
入れると test MAE が約1,300 → 約800 円/㎡に「改善」するが、
実運用では「翌年の価格」を知るために「翌年の前年価格」が必要という循環になる。

**Q17. リークをどう防いだか（仕組みとして）。**
4層で防いでいる。
1. **ホワイトリスト**: `features.feature_columns()` が唯一の特徴量定義。
   リーク列は `include_leakage=True` を明示しない限り絶対に入らない。
2. **時系列分割**: train と test を別の年にし、地点も排他にする
   （`build_split` が重複をアサート）。
3. **前処理の fold 内閉じ込め**: 補完・スケーリング・エンコードを
   `ModelPipeline` 内で fit するので、全データの統計が混ざらない。
4. **テスト**: `tests/test_no_leakage.py` が
   既定の特徴量にリーク列が含まれないこと、
   リーク列を入れると train/test ギャップが崩れること、
   ラグが目的変数を再現しないことを検証する。

**Q18. リークを見つける具体的なサインは。**
(1) スコアが**良すぎる**（R² > 0.99）、
(2) train と test のギャップがほぼゼロ、
(3) 特徴量重要度が1列に集中、
(4) 交差検証の分散が異常に小さい。
本プロジェクトでは実際に (2) と (3) が発生した
（リーク列ありだと test MAE 802・train MAE 524 でギャップ 1.5 倍、
重要度が `num_lag_unit_price` に偏る）。
`tests/test_no_leakage.py::TestLeakyColumnsBehaveLikeLeakage` は
この「リーク特有の振る舞い」自体をテストにしている。

**Q19. 前年価格を特徴量に使うのはリークではないのか。**
**使う年の持ち方が違えば正当**。本プロジェクトは
ファイル内の `前年価格` 列（＝同じ年に閉じた情報）は使わず、
**前年ファイルから地点キーで結合した実測値** `lag_unit_price` を使う。
これは「翌年を予測する時点で実際に手に入る情報」であり、
通常の時系列予測における自己ラグ特徴量と同じ扱い。
区別を明示するため、両方を別の列として保持している
（`prev_unit_price` = リーク列、`lag_unit_price` = 正当なラグ）。

### Feature Engineering

**Q20. どんな特徴量を作ったか。**
- **数値**: 地積、間口比率、奥行比率、前面道路幅員、駅距離、建蔽率、容積率、階数
- **派生**: 容積建蔽比（容積率÷建蔽率 = 開発強度の代理）、
  駅距離帯（公式の区分に準拠した7段階）、地積帯（8段階）、道路幅員帯（6段階）
- **カテゴリ**: 区市町村、用途区分、利用の現況、構造、前面道路区分・方位、
  防火地域、最寄駅、標準地名、都分類地区
- **ラグ**: `lag_unit_price`（前年ファイルから結合した実測の前年単価）
合計 **24列**（数値10 + カテゴリ14）。

**Q21. 帯化（ビニング）の効果は。**
駅距離は最大 7,000m まで裾が長く、等幅ビンだと 95% が1つのビンに入る。
公式の「駅からの距離」区分（100m/250m/500m/1km/2km/5km）で
不等幅に区切ることで、**非線形な距離減衰**を線形モデルでも表現できる。
実測では `ridge` の重要度で `site_area_band` と `nearest_station` が上位に入り、
帯化した特徴量が実際に効いていることが確認できる。

### MAE

**Q22. MAE とは。RMSE とどう使い分けるか。**
MAE = 絶対誤差の平均。外れ値に頑健で「典型的な誤差」を表す。
RMSE = 二乗誤差の平均の平方根。大きな誤差を重く評価する。
本プロジェクトは **MAE を主指標**にした（円/㎡で直接解釈でき、
山林〜都心商業地という5桁の外れ値に引きずられにくい）。
RMSE も併記し、**MAE と RMSE の差**から外れ誤差の大きさを読む。
例: LightGBM の test は MAE 1,347・RMSE 4,626 円/㎡で、
RMSE が MAE の 3.4 倍 = 少数の巨大な誤差が存在する。

---

### RMSE

**Q23. RMSE が MAE よりずっと大きいとき、何が言えるか。**
誤差分布の裾が重い、つまり**大多数は当たっているが一部で大きく外している**。
本プロジェクトではまさにこれで、誤差分析の結果
外れの上位は都心の高容積率商業地と島しょ部に集中していた。
この差があるときは平均値だけで語らず、
**分位点（中央値・90パーセンタイル）と上位誤差地点の実例**を必ず見るべき。

### R²

**Q24. R²（決定係数）とは。負になることはあるか。**
`1 - SS_res / SS_tot`。平均値を予測するだけのモデルと比べて
どれだけ誤差を減らせたかの比率。**負になり得る**（平均より悪い場合）。
本プロジェクトの `median` ベースラインは test R² = **−0.081** で、
これは「学習年の中央値を固定で返す」ことが
「テスト年の平均を返す」より悪いという意味。
`lag` ベースラインは R² = 0.978、LightGBM は 0.914。
R² は分散の大きいデータほど高く出るので、
**MAE と併記しないと誤解を招く**（本プロジェクトは必ず両方出す）。

### Random Forest

**Q25. Random Forest の仕組みと、このプロジェクトでの結果は。**
決定木を bootstrap サンプルで多数作り、各ノードでランダムな特徴量部分集合から
分割を選び、予測を平均する（bagging + feature randomness）。
分散を下げる効果がある。
本プロジェクトでは test MAE 1,282 円/㎡・R² 0.949 で
**7モデル中 best（ベースラインの lag を除く）**。
ただし train MAE 114 円/㎡で**過学習ギャップ 11.2 倍**と最も極端。
`min_samples_leaf=2` でもこの状態で、
「地点を丸暗記している」ことが数値で見える。

### Gradient Boosting

**Q26. Gradient Boosting と Random Forest の違いは。**
Random Forest は**独立な木を並列に作って平均**（分散を下げる）。
Gradient Boosting は**前の木の誤差を次の木が修正するよう逐次学習**（バイアスを下げる）。
一般に GB の方が少ない木で高精度だが、学習率・木の数に敏感で過学習しやすい。
本プロジェクトでは GradientBoosting が test MAE 1,287 円/㎡
（RF とほぼ同等）で、train MAE は 88 円/㎡と**さらに小さい**。
つまり**バイアスは下がったが汎化は改善しなかった**。
これはデータ側の制約（2,560地点・空間自己相関）が支配的であることを示す。

---

### LightGBM

**Q27. LightGBM の特徴と、このプロジェクトでの使い方は。**
(1) ヒストグラムベースの分割で高速、
(2) **Leaf-wise 成長**（レベル単位ではなく損失減少最大の葉を分割）、
(3) GOSS によるデータサンプリング、
(4) **カテゴリ特徴量をネイティブに扱える**（順序を仮定せず最適分割を探索）、
(5) 欠損値をそのまま扱える。
本プロジェクトでは `num_leaves=31`、`learning_rate=0.05`、`n_estimators=600`、
`min_child_samples=20`、`subsample=0.9`、`reg_lambda=1.0`。
カテゴリ列は `LGBMCategoricalRegressor` が
**エンコード後の列位置を明示的に宣言**して渡している
（宣言しないと整数コードを数値として扱い、存在しない順序を仮定してしまう）。
結果は test MAE 1,347 円/㎡・R² 0.914。RF よりわずかに劣るが学習は 0.5 秒。

**Q28. 欠損値をそのまま扱えることの利点は。**
`lag_unit_price` は 1.6%（42地点）が欠損する（新規選定地点）。
LightGBM は欠損を「最適な方向に分岐する」扱いにするため、
**補完による作為的な値の注入が不要**。
一方 `ridge` は中央値補完が必要で、
本プロジェクトは `SimpleImputer(strategy="median")` を
Pipeline 内で fit させている（学習 fold の中央値のみを使用）。

### 特徴量重要度

**Q29. 特徴量重要度の種類と注意点は。**
(1) **Split/Gain ベース**（木が分割に使った回数・ゲイン）: 高速だが
    高基数のカテゴリを過大評価し、相関する特徴量間で希釈される。
(2) **Permutation importance**: 汎化性能への寄与を測るが計算コストが高い。
(3) **SHAP**: 理論的に望ましいが依存が増える。
本プロジェクトは (1) を採用し、**注意点を明示**している:
ワンホットで膨らんだ列は**元の特徴量単位に合算**し、
全モデルを同じ特徴量名で比較できるようにした
（`expand_feature_names` + `feature_importance_table` の `expander`）。
また線形モデルは**標準化済み係数の絶対値**を使い、
「スケールの違う係数を直接比較しない」ようにしている。

**Q30. 重要度の結果から何が分かったか。**
`lag_unit_price`（前年単価）がシェア 36.9% で圧倒的首位。
続いて地積 10.3%、容積率 7.4%、前面道路幅員 6.9%、最寄駅 6.7%。
つまり **「去年の価格」＋「土地の物理的属性」**でほぼ説明でき、
残差に効くのは都市計画（容積率）と立地（駅距離）。
この結果は前年単価ベースラインが最強であることと整合する。

### 対数変換

**Q31. なぜ対数変換するのか。いつすべきでないか。**
(1) 右に裾を引く分布を対称化し、線形モデルの誤差仮定と整合させる、
(2) 二乗誤差を**相対誤差**に変えるので、高額地点が損失を支配しなくなる、
(3) 乘法効果を加法効果に変換できる。
本プロジェクトの目的変数は 0.2〜147,797 円/㎡（5桁）で歪度 17.2、
log1p 後は歪度 −0.7。
すべきでないのは (a) ゼロや負値があるのに素の log を使う場合（log1p で回避）、
(b) 誤差を**円/㎡で解釈したい**場合（必ず `expm1` で逆変換してから指標を計算する）。
本プロジェクトは `TargetLogRegressor` が `log1p` で学習し
`expm1` + 0 クリップで逆変換、指標はすべて円/㎡で報告している。
**このプロジェクトの実測結果（予想と逆でした。`reports/improvements.md` の実測値）**:

| model | 目的変数 | test MAE | test R² |
|---|---|---:|---:|
| ridge | raw | **1,366** | **0.939** |
| ridge | log1p | 1,627 | 0.728 |
| random_forest | raw | **1,282** | **0.949** |
| random_forest | log1p | 1,303 | 0.947 |
| gradient_boosting | raw | **1,288** | **0.948** |
| gradient_boosting | log1p | 1,294 | 0.946 |
| lightgbm | raw | 1,348 | 0.914 |
| lightgbm | log1p | **1,330** | **0.923** |

「線形モデルは対数変換で改善するはず」という予想に反し、**Ridge は raw の方が良く**
（1,366 対 1,627）、逆に **LightGBM は対数変換でわずかに改善**しました（1,348 → 1,330）。
理由は、この目的変数が**極端な下側の外れ値**（山林 0.2 円/㎡）を持つためです。
raw の二乗誤差では安い地点の誤差がほとんど無視され、
対数変換すると逆にそれらが**過大に評価**されます。
MAE は絶対誤差なので raw の方が素直に効き、R² は分散説明率なので
対数空間の方が安定した、という分解ができます。
**「対数変換は常に効く」わけではない**ことを実測で示したのがこの実験の価値です。

### カテゴリ変数の扱い

**Q32. カテゴリ変数のエンコード方法と、このプロジェクトの選択は。**
- **One-Hot**: 順序を仮定しない。高基数だと次元が爆発する。→ **線形モデル（Ridge）**に使用。
  本プロジェクトでは 14カテゴリ列が **235列**に展開された。
  `min_frequency=10` で出現10回未満のカテゴリを
  `infrequent_sklearn` に集約し、次元爆発と過学習を抑えている。
- **Ordinal**: 整数コード。木モデルは分割に使えるが、
  **整数値の大小を順序として解釈させてはいけない**。→ **木モデル**に使用し、
  `LGBMCategoricalRegressor` が列を**カテゴリとして明示宣言**することで
  LightGBM に最適分割を探索させている。
- **Target Encoding**: 目的変数の統計量を使うため**リーク源**。
  CV 内で計算する慎重な実装が必要で、本プロジェクトでは**採用していない**。
- **欠損**: `"unknown"` という明示的なカテゴリとして扱う。
  実データに `用途区分` が空欄の地点が 34 件実在し（山林・農地）、
  これは「値が無い」ではなく「区分が存在しない」という意味を持つ情報だから。

### その他

**Q33. このプロジェクトの最大の限界は。**
3点。(1) **地価であって取引価格ではない**（鑑定評価額）、
(2) **東京都のみ・年1回更新**（月次予測は原理的に不可能）、
(3) **地点数が 2,560** と少なく、空間的自己相関が強いため
**未知の地域への外挿性能は保証できない**。
これらはすべて README の Limitations に明記している。

**Q34. 実務でこれを使うなら、次に何をするか。**
(1) 緯度経度や町丁目レベルの空間特徴量を追加（最大の改善余地）、
(2) 分位点回帰で予測区間を出し、不確実性を提示、
(3) 取引価格データ（不動産取引価格情報）と突き合わせて
地価との乖離を検証、(4) モデルの鮮度管理（年1回の再学習パイプライン化）、
(5) 説明責任のため SHAP で地点ごとの根拠を提示。

**Q35. テストは何を書いたか。**
4ファイル。
`test_cleaning.py`（生ファイルの行数・キー一意性・数値/和暦/階数のパース・
構造的除外ルール）、
`test_features.py`（特徴量契約・帯化の境界・地点キーの年度間安定性・
重複キーの拒否・目的変数の定義）、
`test_models.py`（全モデルの構築と予測・再現性・
ベースラインを上回ること・重要度の整合性）、
`test_no_leakage.py`（**リーク検査**・ラグが目的変数を再現しないこと・
分割の排他性と再現性）。
合計 90 件以上のテストがあり、`pytest` で全通過する。
